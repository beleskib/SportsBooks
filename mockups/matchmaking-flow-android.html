Matchmaking — UI/UX

The “find someone to play with” surface. Built on top of the existing booking system: every match runs at an approved venue (or with an approved coach) at a real, hourly time slot. Player-side ratings (skill / sportsmanship / punctuality — already on UserDto) feed back into who shows up in your match feed.

Domain pieces already in place: MatchDto, MatchStatus, MatchType, MatchVisibility, SkillLevel, ParticipantRole, ParticipantStatus, LobbyDto, BookingParticipantDto, SplitPaymentDto, PlayHomeScreen.

State machine

Match.status = open → filling → locked → in_progress → completed · or cancelled. Transitions: open→filling on first join · filling→locked when last seat fills OR 4h before start (whichever first; charges everyone) · locked→in_progress at slot start · in_progress→completed at slot end (triggers rating prompt).

Trust gate

Matches can only be hosted at venues / coaches with approval_status = 'approved'. The "Find venue" search in step 4.2 reuses the same public read path the discover feed uses, so pending listings are invisible. Player reputation (skill / sportsmanship / punctuality) is already on UserDto and ranks candidates in the matchmaking algorithm.

Cost split

Use SplitPaymentDto. On join, capture an authorization for the player's share. Charge all authorizations when state hits locked. Free cancel up to 4h before start; after that, refund the leaver only if a backfill joins, otherwise their share covers the seat.

Visibility

MatchVisibility already supports public / friends / private. Friends-only feed needs a has_played_with(user_a, user_b) check (we have the booking participants table) — public feed query stays as-is plus a visibility filter.
