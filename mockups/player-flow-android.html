Player flow — Android

End-to-end mockups of what a player sees: onboarding → discovering venues / coaches → picking a time slot → paying → managing bookings → leaving a review. Players never see pending or rejected listings; the public feed only returns rows where approval_status = 'approved', which keeps the player surface trustworthy while partners are still cleaning up their submissions.

Players never see a pending or rejected venue/coach in any of the screens above. The repository layer filters approval_status = 'approved' on every public read path (venue.repository.ts, coach.repository.ts), and the same partial index backs that filter so the feed stays fast as the catalog grows. The result: when something is visible to a player, an admin has already reviewed it — which is the entire point of the pivot.
